## What's in this repo

Time series migration pipeline: extract from Xellent (EMS_TIMESERIES/EMS_TIMESERIESVALUES), optional gap-fill, JSON export, and POST to Settl.

**CLI (`TimeSeries.Cli`)**
- `extract` — Xellent → JSON on disk
- `snapshot` — stores everything `post --all` reads from Settl (list, delivery statuses, current delivery status section only, time series list) and Xellent (children, contracts) under `output/snapshot/<env>/` as JSON lines; resumes, never stores time series points or consumer data. `post --all --offline` reads from it (misses read live and added). A batch dry run never reads points: it asks Xellent for counts per segment (count on/after the boundary, first such point, count before), cached in the snapshot per window when offline. The seed ends with a done check: it runs the batch's own decisions over the snapshot and, for each MP that would be posted, asks Settl for a points summary in that window (the skip-if-existing check); MPs with points go to `done.jsonl` in the same folder. The check runs in parallel, stops at the first year-chunk with points, and caches every summary answer in the snapshot (staleness accepted by the user). A live batch post also marks each MP it posts done. Every `post --all` leaves done MPs out before `--skip`/`--limit` count. `snapshot --refresh` re-reads everything but keeps `done.jsonl`. MPs whose current Settl payer (`payersForMeteringPoints`, cached as `settl-payer.jsonl`) is in the 6##### series (`^6\d{5}$`) are not migrated: every `post --all` leaves them out before `--skip`/`--limit` and lists them in `skip-payer-6-series.csv`; without a payer client (the dashboard, until it passes one) the check logs that it is not active. The seed stores a done summary (`done-summary.jsonl`) and prints "Migration: X of Y done"; `post --all` prints the same line at start. The seed ends by counting Xellent points for every candidate in the window the reports use (boundary null) into `xellent-point-counts-v2.jsonl`, so `readiness`, `resolution-changes` and offline dry runs read them instead of counting again.
- `readiness` — CSV with one row per MP `post --all` would send: value resolutions, Settl series, missing series, Status (Ready/MissingHourSeries/MissingQuarterSeries/MissingSeries/ResolutionChange/NoValues/NotInstalled/SeriesWithoutAgreement — `NotInstalled` is no values because Xellent has no meter at the address yet, meter point status "Oprettet" (5); `NoValues` is a meter that delivers but has no readings), Reasons (`XellentResolutionMismatch` among them), Detail. Reuses the done-check candidate pass for the windows. MPs already posted (done) are counted in the totals both reports print, but get no row — as in `resolution-changes`. `--offline` reads from the snapshot. Read-only; creates nothing in Settl.
- `coverage` — strictly offline summary from the existing environment snapshot: reconciles every unique Settl MP to the migration scope or an explicit exclusion reason, then reports completed (`done.jsonl`), ready, blocked, remaining readiness-status causes, parent/child totals and account coverage. `--json` includes every account; `--by-account` prints incomplete accounts. A cache miss fails instead of reading live.
- All CSVs (skip files, ambiguity file, resolution-changes, readiness) are UTF-8 with BOM, `;` separated, CRLF, every field quoted — Danish Excel opens them directly. Every one carries a `Type` column (Parent/Child, empty when unknown), and skip log lines end with `(parent)`/`(child)`; the "Run completed" line keeps its plain totals (dashboard parser contract) with a `Parents/children:` line under it. `skip-resolution-change.csv` says whether it is a real change or the known Xellent issue.
- `post` — Xellent → Settl `POST /v1/time-series/{guid}/points` → Settl `POST /api/v1/meteringPoints/{id}/externallyInvoicedPeriods` with `BillableTypes=["Contracts", "ExtraInvoiceLines", "MarketPriceLists", "NationalContracts", "PaymentFee", "MovingFee"]`. Fail-fast on any error. Supports `--dry-run` (extracts + resolves Settl MPs but skips all POSTs). Supports `--all` for batch-posting (profiles are gone; delivery category fixed to `El-ekstern`). Batch mode is Settl-driven: every parent MP in Settl's paged list (`FindMeteringPointsAsync`; children only with `--include-children`), narrowed by `--cos-from`/`--cos-to` (delivery start, Danish dates) and paged with `--skip`/`--limit` (counted in MPs with a delivery start in range, identification order; placed before any per-MP check so batches never repeat each other's skips or failures). The Settl customer is never looked up (merged accounts are not Settl customers). Window from `GET .../deliveryStatuses`: `end` = start of the single `InDelivery=true` status (the revision), `start = max(end − 3 år, delivery boundary)`. The MP is posted for the account whose Xellent contract (header dates, `El-ekstern`) runs on the day before delivery starts in Settl (COS − 1 — migrated contracts are closed that day in Xellent). Held by nobody → skipped as missing in Xellent (`skip-missing-in-xellent.csv`); held by several accounts → fails. The held relationship must be closed as a migration, or the MP fails: the account's contract ends on COS − 1, and the agreement behind it has `EMS_AGREEMENTSTATUSEBIX` = 5 ("Leverance ophørt") and also ends on COS − 1. The window starts no earlier than the account's own contract (followed back through its directly preceding contracts). An agreement whose end is before its start keeps its end and gets an open start. With `--include-children` (also on `readiness` and `resolution-changes`, so the candidate pass matches; on `snapshot` it is on by default — `--include-children false` for parents only), child MPs (Settl relation or the Xellent relation table) are posted too: each uses its own delivery status and its own Xellent contract when it has them, and falls back to its parent's when it has neither — the window end is then checked against the parent. The child's own time series go to the child's own Settl GUID. Settl bug (2026-09): a change of supplier may not be marked `InDelivery=true`; then the start of the MP's current v4 delivery status is used as the revision, whatever its `StartReason` (`Na` or `ChangeOfSupplier`). Such MPs also show `InDelivery=false` with no delivery period in Settl's list, so batch mode checks MPs the list shows as not in delivery too. For those: no current delivery start → counted as never delivered; no clean migration in Xellent (no holder, several holders, not closed as a migration) → skipped as not migrated (`skip-not-migrated.csv`), not failed. The close check applies to them even under the window override. Before posting, the window end must equal the Danish date of the MP's current delivery-status start in Settl (Settl's "Delivery Status → Period"); otherwise the MP fails. The featuretest-only rolling window (`windowEndDateOverride`) is exempt.

## Identifier-system

Tre identifier-typer der IKKE må forveksles:
- **EAN** (`Einvoiceeannum`) — e-fakturering (OioXml). Intet med metering points at gøre.
- **Metering point identification** (`ExuDelpoint.Meteringpoint`, 18-cifret) — nationalt MP-ID. Bruges til Settl-lookup via `SearchByIdentificationAsync()`.
- **Settl GUID** (`MeteringPointDto.Id`) — Settl's interne ID. `post`-kommandoen bruger denne GUID til `POST /v1/time-series/{guid}/points`.

## Settl post-command invariants

- `BillableTypes` on externallyInvoicedPeriods must be `["Contracts", "ExtraInvoiceLines", "MarketPriceLists", "NationalContracts", "PaymentFee", "MovingFee"]` for El metering points (afklaring med Systemate 2026-08-27 — Systemate skriver alle disse skal på for målepunkter). Supersedes earlier finding that `["Contracts"]` alone was used (tried on featuretest 2026-04-15). `CustomerContracts` is not used: Systemate rejected it, not the Settl API. See memory `settl_billable_types.md`.
- Fail-fast: first error (TS post OR externallyInvoicedPeriod POST) aborts the whole run. Same applies in batch mode (one failing MP aborts the entire run) unless `--force`.
- No JSON-from-disk mode — `post` always re-extracts from Xellent.
- Batch mode (`--all`) takes its MPs from Settl, never from DataMigration profile files. Window and ownership rule as described under `post` above.
- Each Xellent series (`EMS_TIMESERIES` row) supplies only the days its company's agreement covers (`EMS_TIMESERIES.COMPANYID` + MP → `EXU_DELPOINT` → `EXU_AGREEMENTTABLE`), narrowed to the `EXU_TIMEREADINGSPERIOD` rows at its own resolution (0 = hour, 1 = quarter). The externallyInvoicedPeriod per segment is that period cut to the window, in Danish dates. A series with points but no agreement/reading period, or an empty/inverted period, fails the MP. Known Xellent issue: a reading period at a resolution the company has no series for, while a series of the other resolution holds values there (MP 571313185621006160: quarter-hourly reading from 2023-04-26, only an hourly series with hourly values to 2025). Decision 2026-09-14: the stored values always win. A reading period at a resolution the company has no series for counts as the stored series' own (touching periods merged into one segment), so the values are posted at the resolution they are stored at, for the whole window — no resolution change, no failure. The MP is still listed in `known-issue-xellent-resolution.csv`. In `resolution-changes` such a meter is left out (it is no switch for Systemate) unless Settl has no series of the stored resolution — then it is listed, because the values can't be posted. There is no `--trust-hourly-values` flag; this is the only behaviour. `resolution-changes` (columns `MeteringPointId;ChangeDate;XellentResolutions;SettlSeries;MissingSeries;WindowStart;WindowEnd`) lists MPs whose resolution is not settled: the posted values change hourly → 15-minute inside the window (ChangeDate = the first 15-minute point after the hourly ones; read from the values, not the reading periods), or the values are in a resolution Settl has no series for (`MissingSeries` — Systemate must create it; ChangeDate is then the delivery start, where the posted data stops and Settl's own begins). Only the hourly direction is listed: a switch the other way, a meter already on 15 minutes when the window opens, and 15-minute values against an hourly Settl series are all left out; a meter whose reading period switches while every posted point stays hourly is not one either, and is on the list only for a missing series. MPs Settl states no delivery for (no `InDelivery=true`, revision from the current delivery status) are also off that list — their window, and so the switch date, is not settled; they go to `<out>-unclear-delivery.csv` instead.
