# Settlement config proposals (US 45873)

- The primary output is the existing settlement configuration JSON: `segments` and `schedules` groups.
- Xellent identity and the electricity contract pinned at COS minus one day determine the proposal. All relevant private customers' dated Charge_Abo products are read, regardless of current Settl contracts.
- Private charging follows Eje > Leje > Privat. Privat fallback requires a successful charging-source read and a charging template; failed reads and unrelated missing templates remain visible.
- Customer-level schedule conflicts use only the exact approved `scheduleConflicts` rules. Current Settl groups never select a proposal or fill missing source data.
- The additive `review` array uses these same proposal groups. It contains source account, contract number, electricity products, billing plan, template, dated charging products, current Settl segment ID/name, group-derived current schedule and unresolved reasons. Missing assignments and failed reads have separate messages. Assignment differences and charging-ownership comparisons are not emitted.
- Current assignment `NotAssigned`, `NotRead`, `ReadFailed`, and `Unmapped` statuses have separate problem messages. Partial group reads are treated as unavailable. An assignment-read failure cannot invalidate an otherwise resolved Xellent proposal.
- Existing unmapped groups retain their raw-code values and `mapped:false` for compatibility; review does not label them resolved proposals.
- The legacy rule-comparison block is no longer produced; `--no-comparison` remains accepted for command compatibility.
- Read-only command: `export-settlement-config --env production --output settlement-config.json --disable-representative-merge`. Choose the environment and merge mode matching the original migration; `--limit` is only for smoke tests, not a complete customer review.
- The September XLSX is the original exported baseline, not current Settl assignments. Compare it by customer number with the JSON using the companion dashboard `tools/settlement-review` utility. Keep the email's 82 Privat cases, five Eje cases and seven correction examples in that review; do not hardcode them as production overrides.
- No Settl mutations are performed. CI publication of the OpsCli package is required before the dashboard can run this producer change. Do not use an ad hoc local package feed.
# Historical date selection

The runner's optional `progress` callback emits `SettlementConfigProgress(Stage, Done, Total, Unit)`. It reports actual completed work, including failed or missing reads; it does not count successful proposals or estimate overall completion. Strict-list inventory counts unique supplied IDs, accounting for missing IDs when enumeration ends. History and payer counts include only selected parent points; historical payer progress advances after both dated boundary reads and stays in one phase across differing dates. Directory, group and assignment counts describe their existing read loops. SQL phases have unknown counts. Counters belong to each invocation, so rerunning the same runner starts again at zero. English stage keys are `MeteringPointInventory`, `CustomerDirectory`, `FirstDeliveryHistory`, `HistoricalDeliveryHistory`, `HistoricalPayers`, `CurrentPayers`, `ContractParts`, `Representatives`, `Exemptions`, `ExemptionCustomers`, `CustomerIdentities`, `SettlementGroups`, `ChargingHistory`, `CalculatingProposals`, `SegmentCatalog`, `CurrentSegments`, `PreparingJson`, and `JsonWriting`. Units are `meteringPoints`, `customers`, `groups`, and `files`. Hosts own their completion/failure and Excel-writing stages. Progress does not change JSON or source queries.

With a change-of-supplier date, the exporter reads actual Settl delivery history for every parent metering point, including points no longer in delivery today. A supplier-change period starting on the selected Danish date selects the customer who held the point on that date. The export includes that customer's other points only when both delivery and payer ownership are valid on the same date. A later move-in does not change the supplier's original delivery start or the original customer's COS−1 Xellent basis.

Delivery and payer ends are exclusive. Delivery must cover the whole Danish day; payer lookups at the day's start and last instant must identify the same single customer. Multiple payers for one customer are allowed; different customers are unresolved regardless of primary-payer flags. Missing, failed, malformed or overlapping history is reported without falling back to current relationships or Xellent representatives. The confirmed historical Settl number must match either the dated Xellent contract account or its representative, using the same production account-padding candidates for both. A changed or missing representative cannot invalidate an exact dated-account match. A known customer's incomplete portfolio or a mismatch with both account forms prevents a partial assignment.

The additive `historicalSelection` JSON field identifies the date and source APIs and lists metering-point issues. These may include points whose cohort membership could not be established, so they indicate an incomplete population. Existing files without this field do not establish historical ownership. Current customer assignment values/read statuses remain available; metering-point contract ownership comparisons are withheld. Exports without a selected date keep their current-delivery behavior.

A customer's unresolved source or historical ownership can still block proposals for its other selected points. Coverage names known blocking selected metering points and their actual reasons on the affected rows; the blocking point keeps its own specific problem. Historical reads retain the existing link between an issue and any known customer seen by the dated payer checks. Causes are grouped and formatted once per customer and restricted to output IDs. Each affected row names the first ten blocking IDs in sorted order, then states the remaining count; all specific issues remain in the JSON unresolved rows. If the customer-to-issue link is unavailable, the generic incomplete-information warning remains rather than inventing a point or reason. This changes explanations only; customer-wide blocking, selection and proposals are unchanged.

## Strict metering-point list

Optional `--metering-points` selects only the supplied 18-digit IDs, preserving duplicate counts but calculating each unique point once. It requires `--cos-date` and cannot combine with `--limit`. The supplied date applies to every listed point; the existing electricity contract-part/log resolver reads COS minus one day. The dated raw Xellent account supplies the customer number, formatted by `CustomerNumberPolicy` for the environment, without representative merging. Identity reads use that exact raw account. No unlisted point or sibling contributes. Settl inventory, delivery history, dated payers, customer directory, current segments and settlement groups are not read. Intentionally skipped assignments have status `Skipped` and do not create read-failure problems. List output uses `customerResults`: one known customer result with common proposals/problems and nested `meteringPoints`. Every unique selected point occurs once; each unknown customer point has its own null-customer result. The list output omits `meteringPointCoverage`; older/date-only exports retain it. `meteringPointSelection` records counts, the supplied date, `dateSource: SuppliedChangeOfSupplierDate` and `customerSource: XellentContractAtChangeOfSupplierMinusOne`. The non-list and historical date-only paths retain their existing rules.

The settlement-only electricity and charging readers include live contract parts and ContractPartLog. Electricity retains its exact contract-end=COS-1 rule and complete area/company/agreement/category keys. Charging keeps the existing contract-number/data-area header join because header and part company IDs can differ. Charging now shares the unchanged AboRabat restoration helper: employee `Xellent` changes from 2026-09-04 12:53:27 through 13:35:43 reconstruct the pre-migration state from the first ordered change, including supported deletion chains. Other ordered end changes can explain a live part's original end but do not resurrect unsupported deletions. Missing evidence, start changes and conflicting date-relevant identities remain unresolved. Parts proven to start after COS-1, and expired states, do not block that date. Duplicate products are counted once and Eje > Leje > Privat is unchanged. A genuine charging source failure still withholds the customer's segment; successful points keep their own read status and the affected coverage rows name the selected points whose account/date caused blocking. Reader exceptions remain separate from ambiguous histories.

`contractPartEvidence` records the selected electricity links, complete source attachment keys and logged record IDs. `chargingContractPartEvidence` records selected account/date charging products and ambiguous histories. Existing historical selection, exemptions, E18 priorities and warnings remain in JSON. The single-sheet Excel flattens list `customerResults[].meteringPoints` or legacy `meteringPointCoverage`; detailed evidence remains in JSON. The general account resolver and live-only charging reader keep their previous behavior for unrelated callers.

Charging evidence additionally retains each raw live/log row's change type and employee, ordered log IDs/times, restoration status, reconstructed end, chosen end-evidence log ID/time and whether the selected reconstructed row is active at the reference date. Future exclusions and uncertain rows remain visible. The added fields are optional; old JSON cannot prove migration restoration if these log fields or live state are absent. The representative 347772 regression uses the saved dates/IDs with explicit type/employee/live-state assumptions; a production rerun must verify the actual source values.

Optional exemptions remain off by default and are a current read. When requested in list mode, only selected IDs are searched in Settl; billing is read by the returned GUID, current payers are checked, and customer details are fetched once per referenced customer GUID. No complete customer or metering-point inventory is loaded. Current exemptions affect the proposal only when the current customer matches the dated Xellent customer. Missing Settl points and failed or different ownership reads prevent exemption application and leave Xellent proposals intact. Historical validity remains unverified and is reported.

## Optional current exemptions

`--with-exemptions` reads current Settl exemptions, including for a selected historical date. For a historical date, current exemptions are used only when the current Settl customer matches the customer selected for the export. Billing and exemptions follow the customer and do not transfer to a later customer on the same metering point. Different, missing, ambiguous or failed current-customer reads are reported and keep the proposal unchanged. For a matching customer, historical applicability remains unverified. Any eligible current exemption on a selected metering point changes a resolved, mapped CVR customer's proposed segment to `Erhverv_UG`; `SME` and `Erhverv_ProduktionE18_UG` retain priority. Without exemptions the Xellent proposal stays unchanged. Schedules and unresolved source cases are unchanged.

The additive `exemptionReview` block contains `requestedDate`, `readAt`, `meteringPoints` and `customers`. Metering-point rows retain exemption IDs, type, product element ID and percentage, distinguish `Read` from `ReadFailed`, and mark historical validity `NotVerified`. This includes successful empty current lists: these do not prove that the historical day had no exemption. Customer rows show the original Xellent proposal and final segment and whether it changed. Current exemptions are not described as dated customer facts. List-only named exceptions are documented below.

## E18 production segment

A customer with Xellent CVR identity or a mapped SME proposal receives `Erhverv_ProduktionE18_UG` when at least one owned, scoped metering point is E18 at COS minus one day. Xellent raw `PROD` means E18; `D18`/OtherProduction does not. This rule wins over ordinary template/multiple-segment answers, SME and current exemptions. Other private/CPR customers remain unchanged. It supplies a segment even when an ordinary template is missing or unmapped, but never rescues unresolved historical ownership or incomplete portfolios. Schedules are unchanged.

Type periods are read using the complete delpoint/company/dataarea/delivery-category/attachment key from the chosen owning contract and matched to the reference date. No current-type fallback is used. Missing, overlapping or failed type reads are reported in `e18Review.issues`; without a confirmed E18 an eligible customer's segment remains unresolved if any scoped type is unknown. A confirmed E18 is sufficient, while other type-read issues remain visible. `review.xellent` includes raw `meterPointTypeCode` and `meterPointTypeReadStatus`. `e18Review.customers` shows original and final segment and the E18 metering-point IDs. Optional exemption review remains consistent with the final production proposal and identifies `appliedRule: E18` without crediting an exemption for that change.

`exemptionReview.meteringPoints.customerNumber` identifies the selected export customer. `currentCustomerNumber`, `currentCustomerNumbers`, `currentCustomerReadStatus`, `attributionStatus` and `attributionReason` record the current ownership check. Historical application requires `SameCustomer`; `DifferentCustomer`, `CurrentCustomerMissing`, `CurrentCustomerAmbiguous`, `CurrentCustomerReadFailed` and `SelectedCustomerMissing` prevent only the exemption change, never the segment or schedule proposal. `NotRequired` is used only when no historical date was selected. Several payers for one customer are allowed; different customers are ambiguous regardless of primary-payer flags. Reads are dated to the current instant and expired/future payer links are excluded.

## List customer agreement and named exceptions

Each selected point is mapped independently with the existing identity, dated charging, E18 and optional exemption rules, using loaded sources without additional reads. Mapped aliases agree. A common field is present only when every point has that value and all agree; missing values keep their existing errors. Conflicting mapped segments clear only the common segment, and conflicting schedules clear only the common schedule. Nested point values remain visible. Customer conflict winner tables, pooled E18 and pooled exemptions do not choose list-mode common proposals. Genuine customer source failures still block common proposals and name the selected point causing the failure. Primary groups, totals and final audit values reflect these customer results.

`customerResults` records `customerNumber`, `customerName`, `proposedSegment`, `proposedSchedule`, `problems`, and `meteringPoints`. Each nested point records `meteringPointIdentification`, `changeOfSupplierDate`, its individual `proposedSegment`, `proposedSchedule`, and `problems`. Unknown-customer results are never grouped together. Parent problem text is bounded; nested points and structured conflict candidates retain the full selected-point details.

Optional `customerExceptions` is an array of `{ "name": "Hybel Syd*", "segment": "Partner", "schedule": "HalvårBagud" }` rows. The CLI file contains Hybel Nord*, Hybel Sjælland*, Hybel Syd*, and Hybel Midt* with Partner / HalvårBagud; these values are configuration, not hidden code defaults. A config without this section applies no named exceptions. Editing and reloading the file changes the next run without rebuilding the rules.

A name without `*` is exact. One trailing `*` matches its normalized base alone or the base followed by whitespace and any suffix. Matching ignores case and collapses whitespace but preserves punctuation. Hybel Syd and Hybel Syd A/S match Hybel Syd*, while Hybel Sydvest and names merely containing Hybel do not. Exact matches win before wildcards; the longest matching wildcard wins. No customer-number, CVR or fuzzy matching is used.

Every rule requires name, segment and schedule. Missing fields, duplicate normalized patterns, misplaced/multiple stars, catch-all `*`, and unsupported target values produce a customerExceptions config error before source reads. Targets are canonicalized against existing configured segment/schedule names; known dated E18, exemption and charging segment outputs are also supported. The loader and direct runner options both validate rules.

Known name variants matching the same configured rule apply consistently across the selected customer. Different rules or unmatched conflicting names disable the exception and retain the customer-name warning. Evidence retains each point's source spelling. Genuine source failures remain blocking; only superseded mapping warnings for an overridden dimension are removed. `namedCustomerExceptionEvidence` records rule `ConfiguredCustomerException`, `matchedPattern`, `matchMode` (Exact or Wildcard), selected point, original and resulting mapped values and application flags. Raw source evidence is unchanged. Other selection modes do not apply customer exceptions.
